# C4 Model with Structurizr Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace each system's hand-written `dfd.md` with a Structurizr C4 model (`workspace.dsl`).
The agent drafts it, the owner approves it, every risk cites its IDs, and the web app shows it with
Structurizr's own viewer.

**Architecture:**
- A new pure module, `registry/tmreg/c4.py`, reads a strict and safe subset of the Structurizr DSL,
  and computes zones, crossings, DFD roles, and change records.
- `core.Registry` stores model approvals in a new append-only table. It validates risks against
  those approvals, adopts existing DFD-era registers through `tm.was` mappings, and answers route
  queries.
- The web app replaces its DFD page with an Architecture page. It serves Structurizr's static export
  behind its existing lock, after a one-off Docker export with no network.

**Tech Stack:**
- Python 3.11 standard library (tmreg), and Python 3.9 standard library (guard).
- FastAPI and uv (tmweb).
- React, TypeScript, Mantine, TanStack Query, and Vitest (front end).
- Docker image `structurizr/structurizr:2026.09.19`, used only for exports and conformance tests.

**Spec:** `docs/superpowers/specs/2026-11-09-c4-model-design.md`. Its worked example,
`docs/superpowers/specs/2026-11-09-c4-model-example.dsl`, is the first test fixture. Read both. The
spec is the authority; this plan argues from it.

## Plan decisions

These settle what the spec leaves open. The spec has been aligned with P1 to P3.
- **P1:** views use only `include *`. A dynamic view lists its path IDs.
- **P2:** strings contain no `"` or `\`.
- **P3:** crossings are listed in ID order.
- **P4:** `c4.parse` raises on the first structural or safety error. `c4.problems` returns every
  content-rule violation at once, so the agent can fix them all in one round.
- **P5: Before adoption.** A system that has DFD approvals but no model approval is "awaiting
  adoption":
  - the owner's edits still validate against the latest DFD approval and move `dfd_approval_id`
    (today's behavior);
  - AI adds and edits, and `add` in general, need a model approval.
- **P6:** "Live" risk means `review_state != "rejected"`, `status != "retired"`, and `merged_into`
  empty.
- **P7: "Ever used" IDs** are the IDs in every model approval of this register and of the sibling
  register, plus `TB` IDs from either register's DFD approvals.
  - The sibling register is `registry/trial.db` for the real one, and the reverse. It is opened
    read-only (`mode=ro`), and only if that file exists and holds the system.
  - "Reused" means an ID in the file that an earlier approval used but the latest approval of this
    register does not have.
  - For a register with no model approval, an old DFD `TB` ID is reused unless the item carrying it
    lists that same ID in `tm.was`.
- **P8:** the DFD code (`dfd.py`, `test_dfd.py`, and core's `dfd_status`, `dfd_preview`,
  `dfd_approve`, `dfd_details`, `_parse_dfd`, `_dfd_path`, and `DfdStatus`) is deleted in Task 12,
  once its last user is gone. `_latest_dfd` and `dfd_approvals` stay, read-only, for adoption and
  history.
- **P9:** `c4 check` takes no `--trial`. It reads the real register. `c4 status` and `c4 approve`
  take `--trial`.

**Interfaces:**
- Produces, in `c4.py`:
  ```python
  STRUCTURIZR_IMAGE = "structurizr/structurizr:2026.09.19@sha256:721136283c2f9cf1ba69037bc9de136c579d66fdcb2d771cb60546ec68def1a5"
  ID_RE = r"^(A|S|C|K|R|TB|N|I|ENV|SEQ)[1-9][0-9]*$"   # compile with re.ASCII
  KINDS = ("A", "S", "C", "K", "R", "TB", "N", "I", "ENV", "SEQ")
  MAX_BYTES = 512 * 1024
  TAGS = ("Trust boundary", "Data store", "External", "Async")
  class C4Error(ValueError): ...            # message starts "line N: " when a line is known
  @dataclass(frozen=True)
  class Item:   # person, softwareSystem, container, component, deploymentNode, infrastructureNode,
                # deploymentEnvironment, or group (a TB inside a container)
      id: str; kind: str; name: str; description: str; technology: str
      tags: tuple[str, ...]; properties: dict[str, str]
      parent: str | None    # S for C, C for K and for a group, node or ENV for a node
      group: str | None     # the TB group a component sits in
      line: int
  @dataclass(frozen=True)
  class Rel:
      id: str; source: str; destination: str; description: str; technology: str
      tags: tuple[str, ...]; properties: dict[str, str]; line: int
  @dataclass(frozen=True)
  class Instance:
      of: str; node: str; env: str; line: int   # of: a C or S ID; node: an N or TB ID
  @dataclass(frozen=True)
  class View:
      key: str; kind: str; scope: str; env: str | None; title: str
      steps: tuple[str, ...]; line: int  # kind: systemContext|container|component|deployment|dynamic
  @dataclass(frozen=True)
  class Model:
      name: str; description: str; version: str; sha256: str
      properties: dict[str, str]                 # workspace properties
      items: dict[str, Item]; rels: dict[str, Rel]
      instances: tuple[Instance, ...]; views: dict[str, View]
      def ids(self) -> dict[str, list[str]]: ...  # every KIND, sorted by number. SEQ comes from
                                                  # dynamic view keys, and TB includes groups.
      def all_ids(self) -> set[str]: ...
  def parse(data: bytes) -> Model: ...
  ```

**The grammar** (spec §6). The parser is line-based: one statement per line, `{` only at the end
of a line, and `}` alone on a line. Tokens are double-quoted strings (no `"` or `\` inside) or runs
of non-space characters. Statements allowed in each context:

| Context | Statements |
|---|---|
| top | `workspace "<name>" "<description>" {` |
| workspace | `!identifiers flat` (exactly once, first), `properties {`, `configuration {`, `model {`, `views {` |
| configuration | `scope softwaresystem` |
| properties (any) | `"<name>" "<value>"` |
| model | `<A> = person "<name>" "<desc>" [{]`, `<S> = softwareSystem "<name>" "<desc>" ["<tags>"] [{]`, `<R> = <id> -> <id> "<desc>" "<tech>" ["<tags>"] [{]`, `<ENV> = deploymentEnvironment "<name>" {` |
| person, relationship | `properties {` |
| softwareSystem | `properties {`, `<C> = container "<name>" "<desc>" "<tech>" ["<tags>"] [{]` |
| container | `properties {`, `<K> = component "<name>" "<desc>" "<tech>" ["<tags>"] [{]`, `group "<TBn name>" {` |
| group | `<K> = component ...` |
| component, infrastructureNode | `properties {` |
| deploymentEnvironment | `<N or TB> = deploymentNode "<name>" "<desc>" "<tech>" ["<tags>"] {` |
| deploymentNode | `properties {`, nested `deploymentNode`, `<I> = infrastructureNode "<name>" "<desc>" "<tech>" [{]`, `containerInstance <C>`, `softwareSystemInstance <S>` |
| views | `systemContext <S> "<key>" {`, `container <S> "<key>" {`, `component <C> "<key>" {`, `deployment <*\|S> <ENV> "<key>" {`, `dynamic <S\|C> "<key>" {`, `styles {` |
| view | `title "<text>"`, `include *`, `autoLayout [tb\|bt\|lr\|rl]`; a dynamic view takes `<R>` lines instead of `include` |
| styles | `element "<tag>" {`, `relationship "<tag>" {` |
| element style | one of `shape background color colour stroke strokeWidth border opacity fontSize width height metadata description`, followed by a value |
| relationship style | one of `thickness color colour style routing fontSize width position opacity`, followed by a value |

**Parser rules:**
- **Bytes and text:**
  - `sha256` covers the raw bytes.
  - Decode as UTF-8 (`utf-8-sig`), and normalize `\r\n` to `\n` for parsing.
  - Refuse: more than `MAX_BYTES`; invalid UTF-8; any Unicode `Cc` character other than `\n` and
    `\t` (a lone `\r` is one); any `Cf` character (bidi controls, zero-width characters, a BOM in
    the middle of the file).
- **Refused directives and keywords:**
  - Refuse `!` followed by an ASCII letter anywhere in the file, including inside strings. The one
    exception is the single `!identifiers flat` statement.
  - Refuse the statement keywords `extends url icon logo theme themes image perspectives
    terminology users visibility branding filtered custom animation archetypes`, and every
    statement not in the table above.
  - Refuse comments: lines starting with `//` or `#`, and any `/*`.
- **IDs:**
  - Assigned IDs match `ID_RE` (ASCII) and are unique.
  - Every name starts with `"<ID> "`, and every relationship description starts with `"<R ID> "`.
  - A group's name starts with `TB<n> `, and that `TB<n>` is its ID.
  - A dynamic view's key matches `SEQ<n>`, and its title starts with `"<key> "`.
- **What the IDs must refer to:**
  - Relationship ends name defined A, S, C, or K items.
  - Instances name a C (`containerInstance`) or an S (`softwareSystemInstance`).
  - View scopes exist.
  - Dynamic steps are R IDs.
- **Tags:** positional only, comma-separated, and each one in `TAGS`. Style selectors may also name
  Structurizr's built-in tags.
- **Version:** the workspace property `tm.version` becomes `Model.version`. Use dfd.py's
  `_VERSION_RE` rule; a missing or bad version is an error.
- **Block depth:** at most 12 nested blocks.

### Task 2: `c4.py`: content rules, zones, crossings, roles, records, changes

**Files:**
- Modify: `registry/tmreg/c4.py`
- Create: `registry/tests/test_c4_model.py`

**Interfaces:**
- Consumes: Task 1 `Model`, `Item`, `Rel`, `Instance`, `View`, `parse`.
- Produces:
  ```python
  def problems(m: Model) -> list[str]                       # every content rule broken, "line N: ..." in line order
  def role(m: Model, item_id: str) -> str | None            # "External entity"|"Process"|"Data store"|"Data flow"|"Trust boundary"|None
  def where(m: Model, item_id: str) -> list[str]            # e.g. ["S1", "C2", "K3"]
  def zones(m: Model) -> dict[str, dict[str, list[str]]]    # A/S/C/K -> ENV -> TB IDs, outer to inner
  def crossings(m: Model) -> dict[str, dict[str, list[str]]] # R -> ENV -> TB IDs in ID order
  def to_record(m: Model) -> dict                           # canonical JSON-safe record (below)
  def changes(old: dict | None, new: dict) -> dict          # {"added": [...], "removed": [...], "changed": {id: [fields]}}
  def was_map(record: dict) -> dict[str, list[str]]         # old DFD ID -> new IDs claiming it, in ID order
  def next_free(m: Model, used: dict[str, set[int]]) -> dict[str, str]  # kind -> next free ID
  ```
- `to_record` shape:
  - `{"version", "name", "description", "dataclasses": {name: text}, "items": {id: {...}}, "rels": {id: {...}}, "views": {key: {...}}}`.
  - Items carry `kind, name, description, technology, tags, properties, parent, group, role, where,
    zones`.
  - Rels carry `source, destination, description, technology, tags, properties, role, crossings`.
  - Views carry `kind, scope, env, title, steps`.
  - Lists are lists, and keys are sorted when dumped (`json.dumps(sort_keys=True)`).
- `changes` compares items, rels, and SEQ views by ID. The fields it compares are `name, description,
  technology, tags, properties` (minus `tm.was`), `parent, group, source, destination, crossings,
  zones, title, steps`.

**Rules for `problems`** (spec §5):
- **Required text:** every item except ENV and groups needs a non-empty description. C, K, N, TB,
  and I need a technology, and so does every R.
- **Properties:**
  - Allowed names: `tm.version`, `tm.dataclass.<Name>`, and `structurizr.inspection.*` (workspace
    only); `tm.owner`, `tm.zoom`, `tm.enforced_by`, `tm.enforced_by.<TB>`, `tm.zone.<ENV>`,
    `tm.data.stored`, `tm.data.sent`, `tm.data.returned`, `tm.auth`, `tm.assumed`, and `tm.was`.
    Any other name is a problem.
  - `tm.owner` is required on C and K.
  - `tm.enforced_by` is required on each TB node. `tm.enforced_by.<TB>` is required on the
    container of each TB group.
  - `tm.was` holds comma-separated IDs matching `(E|P|D|F|TB)[0-9]+`.
- **Tags:**
  - `Data store` only on C or K, which then need `tm.data.stored`.
  - `External` only on S.
  - `Async` only on R.
  - `Trust boundary` only on a deployment node; such a node's ID starts with TB, and an N may not
    carry the tag.
- **Header:** the workspace has `configuration` with `scope softwaresystem`, and the property
  `tm.version`.
- **Scope:** exactly one S has no `External` tag, and only that S has containers.
- **Zones:**
  - Every A, and every External S that lacks an instance in an ENV, has `tm.zone.<ENV>` for every
    ENV.
  - Its value is a TB node ID in that ENV, or `outside`.
- **Paths:**
  - Every R has `tm.data.sent`, `tm.data.returned`, and `tm.auth`.
  - Data values are `none`, or comma-separated names declared as `tm.dataclass.<Name>`. The same
    applies to `tm.data.stored`.
  - Ends are A, S, C, or K, and differ.
- **Zoom:** `tm.zoom` is present exactly on containers that have components, and matches
  `^[1-7](, [1-7])*: .+`.
- **Deployment:** every container of the scope S has at least one instance in every ENV. Every TB
  node holds at least one node, instance, or infrastructure node.
- **Views:**
  - Required views: `context` (systemContext of the scope S), `containers`, `components-<C>` for
    each C that has components, and `deployment-<ENV>` for each ENV.
  - Every view has a title. Required views' titles start with "System context diagram for",
    "Container diagram for", "Component diagram for", and "Deployment diagram for".

**Zones and crossings:**
- An instance's chain is the TB ancestors of its node, plus the node itself when it is a TB, from
  outer to inner.
- A component takes its container's chain, plus its group's TB at the end.
- A person takes the chain of its `tm.zone.<ENV>` TB node (the node and its TB ancestors). For
  `outside`, the chain is empty.
- A path crosses the symmetric difference of its two ends' chains, unioned over every pair of
  instances. When both ends sit in one container, compare within the same instance.

**DFD roles:**
- A, and an S tagged External: External entity.
- C or K tagged Data store: Data store.
- Any other C or K: Process.
- R: Data flow.
- A TB node or group: Trust boundary.
- The scope S, N, I, ENV, and SEQ: none.

**How the export works:**
- **Inputs:** `export` writes `data` to `<site_dir>/in/workspace.dsl`.
- **The Docker command, exactly:**
  `["docker", "run", "--rm", "--network", "none", "--cap-drop", "ALL", "--security-opt", "no-new-privileges", "-v", f"{in_dir}:/usr/local/structurizr", c4.STRUCTURIZR_IMAGE, "export", "-workspace", "workspace.dsl", "-format", "static", "-output", "site"]`.

  so in the report.

  - exit 0 → `accepted`;
  - any other exit → `refused`, with the last 20 lines of stderr.
  - It writes `<site_dir>/result.json` beside `in/`, so it is never served. It reuses that file for
    the same sha256.
- **Unavailable:**
  - `FileNotFoundError`, or a stderr matching "Cannot connect to the Docker daemon" →
    `DiagramsUnavailable("Docker isn't running. Start Docker Desktop, then open the diagrams again.")`.
  - A timeout → `DiagramsUnavailable("Structurizr took too long to export the diagrams. Try again.")`.
- **Link format:** `view_url` follows the static site's real deep-link format. Find it from the
  exported site, and pin it in a test.

**The export route:** `POST /api/{reg}/systems/{slug}/c4/export`:
1. Call `c4_checked_bytes`. Its errors give a 422.
2. Call `await run_in_threadpool(diagrams.export, ...)`.
3. Return `{"sha256", "state", "message", "base": "/diagrams/<reg>/<slug>/<sha>/", "views": [{"key", "url"}]}`.

`DiagramsUnavailable` gives a 503 with `detail`. The `structurizr` key of `GET .../c4` comes from
`verdict` for the current sha256.

**Serving:** `GET /diagrams/{reg}/{slug}/{sha256}/{path:path}`:
- **Lock middleware:**
  - the Host check applies as for every request;
  - `/diagrams/` needs a valid session cookie (401 without one; no CSRF header);
  - any method other than GET or HEAD gets a 405.
- **The route:**
  - `reg` is `main` or `trial`, `slug` is valid, and `sha256` is 64 lowercase hex characters;
  - the resolved path must stay inside `<site_dir>/in/site`, otherwise 404;
  - an empty path means `index.html`;
  - set `Cache-Control: no-store`;
  - set the CSP: the app's `CSP`, with `script-src 'self'` extended by `result.json`'s hashes;
  - the content type comes from `mimetypes`.
